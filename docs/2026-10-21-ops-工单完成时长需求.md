# OPS 工单完成时长需求

## 1. 当前版本范围

- 只影响新建工单，历史工单保持原数据和原流程。
- 工单状态继续使用原有状态：排队中、进行中、阻塞、已完成。
- 本阶段不增加审核状态、审核列表或通知。

## 2. 完成时长

### 2.1 提单规则

- 新建普通环节工单时，提单人必须填写“完成时长（小时）”。
- 允许范围为 1 至 720 小时，必须是整数。
- 前端提交前必须校验该字段；服务端不因缺少该字段拒绝请求，未传时沿用当前环节系统默认交付时长。
- 服务端根据提单时刻和完成时长计算 `due_at`，后续剩余时间、超时和预警继续沿用原有工时计算逻辑。

### 2.2 制片特殊规则

- 当工单环节为“制片”时，完成时长不可编辑。
- 直接使用系统“制片”环节配置的交付时长；当前系统配置为 1 小时。
- 服务端按环节名称强制使用该配置，客户端传入其他时长也不能覆盖。

## 3. 实现分层

### 服务端

- `ops-routes.mjs`：负责完成时长计算、建单和状态接口。
- `ops-realtime.mjs`：继续负责项目、成员和环节的实时数据组装。
- `company-plan-store.mjs` / Prisma schema：继续使用已有的 `due_in_hours` 字段，不新增审核字段或审核状态约束。

### 前端

- `CreateTicketModal.tsx`：按工单展示完成时长输入；普通环节必填，制片环节禁用并展示系统时长。
- `TicketsPage.tsx`：提交时将每条工单的完成时长传给服务端。
- `TicketTable.tsx`：继续使用原有状态筛选，不增加待审核选项。

## 4. 验收标准

1. 普通环节不填写完成时长时不能提交。
2. 普通环节填写 1 至 720 小时后，工单按该时长计算截止时间。
3. 制片环节输入框不可编辑，创建后使用系统制片交付时长。
4. 服务端未收到普通环节时长时沿用系统默认交付时长。
5. 原有状态、项目、版本、负责人和提单流程不受影响。
