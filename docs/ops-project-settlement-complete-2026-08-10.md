# OPS 项目结算完成逻辑说明（2026-08-10）

## 背景

OPS 项目池当前展示的是项目下的版本状态，项目本身另有项目级生命周期 `projects.lifecycle_status`。

本次新增的 `结算完成` 是一个版本状态，同时会触发项目级生命周期完成，用于管理员在 OPS 项目池中把已回收项目结算完成。

## 状态口径

- `回收中`：版本状态，写入 `project_versions.status`。
- `结算完成`：版本状态，写入 `project_versions.status`，也写入兼容项目主状态 `projects.status`。
- `已完成`：项目级生命周期，写入 `projects.lifecycle_status`。项目生命周期变为 `已完成` 后，OPS 项目池不再展示该项目。

## OPS 端入口

- 入口仍在项目池“修改项目状态”弹窗中，不新增项目状态列。
- 只有管理员可看到 `结算完成` 选项。
- 只有当前行状态为 `回收中` 时，弹窗下拉才追加 `结算完成`。
- 项目池表头“当前状态”筛选不展示 `结算完成`，因为结算完成后的项目会被隐藏，筛选该状态没有数据。
- `结算完成` 选中后会显示醒目提示：
  - 单版本：确认后项目同步为已完成，并从 OPS 项目池隐藏。
  - 多版本：提示这是项目级操作，会让整个项目完成，并要求确认所有版本均已回收。

## 回收交接人

- 版本状态改为 `回收中` 时，如果这是单版本项目，或多版本项目中最后一个待回收版本，必须选择回收交接人。
- 如果多版本项目还有其他版本未回收，暂不要求选择交接人。
- 前端会禁用确认按钮，后端也会兜底校验。

## 结算完成校验

`结算完成` 的最终校验在 helper server 完成：

- 必须是该项目所有版本状态均为 `回收中`，才允许结算完成。
- 如果任一版本不是 `回收中`，接口返回：`多版本项目需所有版本回收中后才能结算完成`。

OPS server 不再用项目主表状态提前判断，避免项目主表旧状态和版本状态不一致导致误拦。

## 结算完成写入

结算完成成功后，helper server 在同一事务中写入：

- `projects.lifecycle_status = '已完成'`
- `projects.status = '结算完成'`
- `project_versions.status = '结算完成'`（该项目所有版本）
- `status_changed_at = 当前时间`
- `projects.operation_log` 追加 admin 操作记录

随后通知 OPS 刷新项目快照。由于项目生命周期已是 `已完成`，OPS 项目池会隐藏该项目。

## 日志

本次会写两类日志：

- OPS 项目池流转日志：记录 `回收中 -> 结算完成`，用于 OPS 项目池流转抽屉。
- Admin 项目操作记录：写入 `projects.operation_log`，例如 `OPS结算完成：项目状态改为已完成`。

此外，普通 OPS 状态流转也会同步追加到 admin 操作记录，例如：

`OPS修改状态：v1 默认版本 推进中 -> 回收中`

## Admin 端

- `结算完成` 已加入 admin 状态枚举和颜色。
- 版本管理中可显示/选择 `结算完成`。管理员可直接修改版本状态，这是管理员权限口径。

## 线上部署注意

部署时需要先发布 helper server，再发布 OPS/Admin 前端和 OPS server。

helper server 启动迁移会自动调整 MySQL enum：

- `projects.status` 增加 `结算完成`
- `project_versions.status` 增加 `结算完成`

如果线上不依赖启动迁移，需手动执行：

```sql
ALTER TABLE projects
  MODIFY status ENUM('未启动','推进中','已完成','已反馈','待反馈','打包中','回收中','结算完成','客户暂停')
  DEFAULT '未启动';

ALTER TABLE project_versions
  MODIFY status ENUM('未启动','推进中','已完成','已反馈','待反馈','打包中','回收中','结算完成','客户暂停')
  DEFAULT '未启动';
```

飞书状态不同步。本流程只保证 helper/admin/ops 数据一致。
